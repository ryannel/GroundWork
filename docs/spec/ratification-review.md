# Ratification review — adversarial findings register

**What this is.** Seven reviewers read the full nine-file spec at commit `16c5ce4` (2026-08-06). Each one worked blind, using a single lens: internal consistency, reasoning flaws, operational failure modes, cost honesty, cold adoption, security and privacy, or life-cycle coverage. The driver ran its own blind pass first, then triaged every finding against the spec text. This file is the curated register; full agent outputs live in the session transcripts.

**This file is evidence, not spec.** Nothing here changes the spec by existing. Each finding needs an owner decision: amend the spec, add it to open items, scope it out, or dismiss it with a reason.

**Status tags.** `confirmed`: driver checked quotes and logic against the spec text. `corroborated`: two or more reviewers found the same issue independently while blind. `plausible`: credible but unverified — the owner should judge it.

**Disposition (2026-08-06).** The owner directed a full fold-in. One ruling reshaped cluster A: tokens, not dispatches, are the scarce resource — small dispatches are fine, total consumption is the real budget. The owner also required host portability, OpenAI-compatible hosts as the minimum bar, so the framework doesn't bind to one vendor. The fold-in landed in four commits. `91aefb5` covered clusters A/F: token economics and honesty reframes. `ed15797` covered cluster B: contradictions. `bdd974b` covered clusters C/D: evidence-layer git reality and the security floor. `1d25731` covered clusters E/G: operational life, the adoption boundary, and the host adapter contract. Security defaults, the flake/release/backward-move machinery, and the single-owner scope statement were driver calls under that mandate, flagged in chat as veto points.

## A. The cost estimates are stale and mix incompatible units

- **A1. The dispatch savings estimate is wrong under the new definitions.** (HIGH, corroborated ×3) loop.md and changes.md still claim "~20 frontier dispatches (from ~35)" — but the two numbers measure different things.
  - Old ~35 = a measured total of all dispatches. New ~20 = an ideal, frontier-only count omitting roles added later: the blind test author, capsule writer, standards cleanup pass, and design-seal adversary.
  - Recounted the same way, a complex bet (3 milestones, 8 slices) costs ~50–60 total dispatches — more than today.
  - Those added roles also have no stated tier, violating index.md's own rule: "leaving it off is an error."
- **A2. The old number includes rework; the new number does not.** (HIGH, confirmed) The old 35–45 figure includes bounce rounds (rework cycles); the new 20 assumes one clean pass. But the blind author is designed to *increase* bounce rounds — priced elsewhere at up to 41% of a build.
- **A3. Complex slices now run through five or six sequential stages.** (MED, corroborated) The chain runs build, handoff/extraction, blind authoring, triage, battery, adversary, capsule — each starting fresh. Throughput is capped by per-slice time, which roughly doubles under this chain. No elapsed-time budget exists, and the journal doesn't record how long any of it takes.
- **A4. The "short brief" the blind author reads is actually design-sized.** (MED, confirmed) On the complex lane, the blind author's input is the full sealed design walk, copied into ~8 dispatches per bet. The milestone-sum adversary must also hold diff, design, tests, and code at once, and write new tests, capped at "three reads, no more." That is the largest context window in the system. The spec calls it a reduction.
- **A5. The "10–15 moments" figure counts pauses, not the decisions inside them.** (MED, confirmed) The headline claim — "10–15 moments → the seals" — treats a pause count as a decision count. One bet-close sitting holds ~15–25 separate decisions: 8 capsules, a row-by-row board read, the drive, the teach-back, batched ratifications, doc approvals, the merge go-ahead. The Map's own decision-budget instrument counts decisions; the headline number should too.
- **A6. The driver's own token spend is missing from the spend accounting.** (LOW, confirmed) Spend-by-role accounting covers only dispatches. The driver isn't a dispatch, yet it assembles every brief, inspects every diff, triages every finding, and runs every teach-back. That likely makes it the system's most expensive part. It is structurally left out of the "sorted column" of spend.
- **A7. The new machinery built to replace prose has no maintenance-cost check.** (MED, plausible) The spec counts words cut to the thousand. But its ~31 new components have no upkeep-cost check: daemon, journal, board derivation, battery, UI-driver toolchains, update engine, sim rig. At one-person scale, upkeep is the documented historic failure mode: 384 commits of it.

## B. Internal contradictions, mostly caused by the order amendments were made in

- **B1. The spec contradicts itself on whether tests come before or after the code.** (HIGH, confirmed) standards.md is plain: "Tests are written first and observed failing before the implementation exists." proof.md contradicts it two ways.
  - The complex lane's accepting test suites are written *after* handoff, not before.
  - proof.md also claims tests are "authored at decomposition, committed red, exactly as today" — a third moment, alongside decomposition headline proofs and auditor extensions.
  - Never reconciled — read literally, the tests-first rule cancels out the blind author.
- **B2. Goal 11's autonomy-scaling rule has no defined computation behind it.** (HIGH, confirmed) Goal 11 says: "Autonomy scales with verification… probe coverage of the touched area, not the task's label." But the dial's actual inputs are owner choice, per-lane defaults (a task label itself), and sensitive paths. doors.md asserts this computation happens, but no file defines it or ties it to the dial.
- **B3. The rule that nobody writes the journal contradicts dev mode's own driver-written event.** (MED, confirmed) The spec says "No human or agent ever writes it" about the journal — yet the driver-written method-friction event appears in that same sentence's list of journal events.
- **B4. The stopping rule claims to be a closed list of five, then adds a sixth item.** (MED, confirmed) The spec introduces it with "A genuine stop is only:" and lists five items. Then, two bullets later, it declares an unaccepted-contract dependency a genuine stop too — a sixth item outside the closed list. A mechanical reading of the list would miss it.
- **B5. The term "open finding" is used with two different, conflicting meanings.** (MED, confirmed) One passage says "A slice cannot close over an open finding." Another refers to "open deferred findings" on the known-gaps view precisely because slices closed past them. The spec implies a finding-state model — "open" blocks closing, "deferred"/"dismissed" don't — but never states it directly.
- **B6. The module graph has a second real consumer that its own retention test ignores.** (MED, confirmed) changes.md says "its one consumer is the ripple caller list," and marks it for deletion if unused. But record.md also relies on it, as the staleness check's way of reaching indirect drift. The retention test, following changes.md, could delete a mechanism the Record depends on.
- **B7. The spec credits the wrong system for catching a schema hole that was missed twice.** (MED, confirmed) index.md credits the catch to "magpie's own mechanical gate," but evidence.md and proof.md place it in staycurrent instead — the loader/gate story behind ADR 0006. This factual error sits in the ratification headline.
- **B8. Nothing actually produces the markdown pages the no-daemon fallback promises.** (MED, corroborated ×2) The spec claims "The same pages exist as committed markdown" when the daemon isn't running. But the six-writes deletion removed that commit mechanism — it moved rendering into the daemon instead. Without the daemon, what's left is raw ledgers, not readable pages.
- **B9. The tower is defined as read-only, but the Queue needs to write somewhere.** (LOW, confirmed) Queue outcomes produce ledger writes and filed issues, but the only named server, the tower, is read-only. No file says where those writes happen.

## C. The evidence layer does not hold up against how git actually works

- **C1. The journal is tied to git history, which is not append-only in practice.** (HIGH, confirmed) Most journal events have no commit to attach to: dial changes, triages, teach-backs, every red run on a reworked or bounced slice. Yet the spec says "a check with no journal lines is a check that never ran."
  - Normal git use breaks it further. Parallel bets appending to one file make every merge conflict. Rebases duplicate lines, and reverts delete lines from what's supposed to be "append-only." That corrupts the evidence layer that governance, sunset, and spend all depend on.
  - Fix direction: store the journal outside the work DAG — git notes/refs, or an owner-level log keyed by commit SHA and session.
- **C2. Squash merges and branch teardown can erase the history the views depend on.** (HIGH, corroborated ×2) A single squash merge collapses a whole bet into one commit with no trailers, erasing the derivation so the bet renders as an unlaned bypass.
  - Seal tags point at commits that leave history once the branch is torn down. "Frozen forever" views are re-derived from refs teardown removes, with no way stated to persist them first.
  - Also an adoption problem: repos with protected branches or squash-merge-only PRs can't grant the assumed git contract — and doors.md never names this as a precondition.
- **C3. Unattended runs have no limits on retries, spend, or detecting a dead run.** (HIGH, confirmed) There's no retry ceiling and no per-slice spend ceiling for a genuinely red row. There's also no way to detect a dead run — quota exhaustion, a crash, or the machine sleeping. In all of these cases, the worker's changes stay deliberately unstaged. The push channel for genuine stops is "optional and deliberately undecided," though bet-level-or-higher dial settings depend on it.
- **C4. The parallel-run design does not address the lock-contention problem it names.** (MED, confirmed) evidence.md describes a 62% worktree index-lock failure rate as "a warning the parallel design must engineer around," but no file engineers around it. Fix direction: one serialized git writer per repo.
- **C5. Tag pushes are missing from the backup process, so seals can go unseen on other machines.** (MED, plausible) Branch pushes are automatic, but tag pushes are never mentioned in the spec. A seal granted on one machine stays invisible to another machine's Map, Queue, and `verify`. The tower reads local clones, and nothing flags when a clone is behind the remote.
- **C6. A stricter existing check, not just a new one, can turn a live board red mid-run.** (LOW, confirmed) The ratchet-arrival mechanism only covers newly *added* checks. A check that becomes stricter instead can turn previously claimed-done proofs red again, stopping every in-flight run. That reproduces, inside the spec's own mechanism, the exact failure mode it warns about elsewhere: "a release that turns projects red."
- **C7. Hook decay goes undetected, even though the spec says hooks don't decay.** (LOW, confirmed) The spec says "Hooks do not [decay]," but in practice they do — host updates, overwritten settings, fresh clones can all break them. Hook firings aren't journal events, so nothing notices when one stops surfacing information: the system quietly reverts to the old invisible model it replaced.

## D. Security and privacy holes in the framework's own infrastructure

- **D1. The tower gathers every project's data at one address with no authentication.** (HIGH, confirmed) The tower holds every registered project's plans, ledgers, and in-flight state at one stable local address. "Authentication," "binding," and "origin" appear nowhere in the spec. So any other user or process on the machine can read the whole portfolio. Through browser tricks, so can a remote web page. The tower's open item covers its lifecycle, not authentication.
- **D2. Dev mode can leak journal data and project details into a public repo.** (HIGH, corroborated ×3) Issues filed in the public framework repo carry journal lines, project file paths, and session IDs, with no redaction step. The auto-file option publishes them without a human ever looking first, and "maintainer" status is just a local flag any adopter can set themselves.
- **D3. Debug mode can commit secrets to git and push them off-machine.** (HIGH, confirmed) Debug mode widens journal lines to include full check output. That output can include secrets-scan results and real-infrastructure logs. It then gets committed into git history and immediately pushed off-machine as a backup.
- **D4. The update engine can push unsigned code into every registered repo's hooks and CI.** (HIGH, confirmed) Hooks run at session start, and CI stanzas auto-reconcile, both by design with no human review — and there's no signing, provenance tracking, or attestation anywhere. The package-hash check only confirms what got installed, not that it's safe: one compromised release becomes silent code execution across every registered project and its CI.
- **D5. The permission model for unattended runs is only written down, not enforced.** (MED, confirmed) The spec calls for "a *stated* permission model" — but its own doctrine elsewhere is that prose alone doesn't hold up. Nothing enforces path allowlists, pins push remotes, scopes credentials, or bounds network access during multi-day runs. And the stopping rule only fires if the agent itself decides its action crosses a boundary.
- **D6. The agents being audited can also alter the evidence that audits them.** (MED, confirmed) The journal, ledgers, and seal tags are plain files and git tags in a repo the agents themselves have full write access to. "Append-only" and "the only way it moves forward" are conventions, not enforced rules. Fix direction: a hash-chained journal, signed seals, and a chain `verify` checks.
- **D7. Probes run an untrusted repo's own commands before any audit happens.** (MED, confirmed) The spec declares a brownfield repo's content untrusted for *reading*. But probes run the repo's own test and build commands the moment sockets are mapped — before any seal or dependency audit.
- **D8. The tower can render untrusted, agent-written docs with no isolation between projects.** (MED, plausible) Markdown written by agents, or seeded from a brownfield repo, gets rendered by the tower with no sanitization, content security policy, or isolation specified. One injected document becomes stored cross-site scripting, with read access to every project's pages.
- **D9. Projects get registered automatically, with no opt-out for private work.** (LOW, confirmed) `init` and `update` register a project unconditionally, with no per-project flag to keep it local-only or excluded — something NDA-bound work would need.

## E. What happens to software after it ships — the spec's blind side

- **E1. There is no fast path for emergencies, and no way for production signals to reach the system.** (HIGH, confirmed) Even the fastest lane runs the full battery, so an unrelated red row at 2am still needs a full sealed-waiver process before anyone can act. Nothing reads the observability data standards require projects to ship — no alert or user report ever reaches the Queue or the Map. The only thing that catches problems after shipping is "the owner, in use."
- **E2. There is no way to formally revert or abort a shipped change.** (HIGH, corroborated ×3) Revert exists only as a capsule *metric*, never a real mechanism. If a capability is un-shipped, several parts of the system still insist it exists: the permanent suite, the manifest (`add-capability` has no matching remove), the Map ("forever"), and the Record.
  - Mid-flight withdrawal — which the historical record shows happening — has no defined end state, leaving stalled-forever lines, undischargeable known-gaps entries, and branch deletions that destroy the evidence.
  - Fix direction: make "reverted" and "withdrawn" first-class states, each with a defined cascade of effects.
- **E3. The spec has no concept of a flaky test.** (HIGH, corroborated ×4) There's no concept of retrying a test, quarantining it, or tracking its flake rate.
  - The board treats red and green as ground truth. One red row counts as a genuine stop even at night. And the pairing rule made the flakiest class of test the headline row of every user-facing proof.
  - Every flake has to route through a full sealed human waiver — building in the exact override-fatigue problem the spec documents elsewhere.
- **E4. The spec's proofs stop at the merge and never reach real deployment.** (HIGH, confirmed) The spec has no product versioning, changelog, release channel, deploy environment, or staged rollout anywhere.
  - It never mentions feature flags. The ban lives in the old delivery contract, not this one. So there's no mechanism for partial exposure, and no stated position on whether one should exist.
  - The front door proves the build works, not that it deployed. Whether something shipped to real users sits outside every proof the spec defines.
- **E5. Performance is named as a baseline but has no row of its own.** (MED, confirmed) standards.md announces "security, privacy, accessibility, and performance baselines," then lists rows for only three of the four — performance is missing. The framework's founding failure case included a 5–10× slowdown that still passed as green. Under this spec, it still would.
- **E6. A dependency vulnerability is detected but has no defined response.** (MED, confirmed) A red dependency-audit row has no assigned lane, owner, or cadence for handling it. A new CVE turns the battery red for slices that have nothing to do with it, and the spec has no "the world changed" state distinct from "you broke it."
- **E7. Data migrations and backfills are not actually proved.** (MED, confirmed) The spec's "migration apply" proof only covers a fresh environment. There's no proof for reversing a migration, no duration category for hour-long backfills, and no rule for where production-derived fixtures come from. Fixtures are policed for being too fake, never for being too close to real production data.
- **E8. Nothing bounds the system's long-term growth in stored evidence.** (MED, confirmed) The journal, archives, frozen views, and delete-nothing test suite all grow without bound, and the per-slice deletion test's cost scales with suite size.
  - By year three, battery latency will quietly break the patch lane's "checks-only cheap" promise. Slow verification is the documented trigger for bypassing the process. Yet nothing sets a runtime budget, tiering scheme, or segmentation to prevent it.
- **E9. The spec has no plan for what happens if the owner changes.** (MED, plausible) Seals are identity-free tags in one laptop's registry, with no handoff artifact, no model for a second person joining, and no onboarding for a new method maintainer. This would be fine as an explicit scope decision — it's a problem only because the spec is silent instead. (See G2.)

## F. Reasoning flaws in the evidence story

- **F1. A keep decision is justified using evidence that no longer exists.** (HIGH, confirmed) The spec claims "Per-slice correctness review was never observed to rubber-stamp." But raw review outputs were deleted for 21 of 23 bets and attribution was never filled in, so the miss rate is unknowable. Keeping per-slice review may be right as a starting assumption — but the spec presents it as measured fact, which it isn't.
- **F2. Only one of three lens changes was actually backed by evidence.** (HIGH, confirmed) The spec claims its lens split is evidence-based, but only the honesty audit was measured.
  - The edge-case lens (named, real catches in a single slice, one build-killing) and the coverage lens (repeated real findings) were both demoted anyway. That happened on the unmeasured claim that milestone-close "gives them more to bite on."
  - Needs an honest unproven label, plus a rollback clause if those problems recur.
- **F3. Clean escalation reports can't be trusted as proof the channel works.** (HIGH, confirmed) The escalation contract exists because cheap models can't reliably judge their own limits — so a dozen reports saying "BLOCKING CONCERN: none" aren't proof the channel works.
  - The rate of missed escalations is unknowable, yet tier policy tunes itself on this flattering, unverified signal.
  - Needs a way to measure *missed* escalations directly — e.g., having the adversary tag findings the worker should have escalated but didn't.
- **F4. The sunset process can't tell prevention from irrelevance, and has too many items to review.** (HIGH, corroborated ×2) For linters, the spec itself admits zero firings looks identical to perfect prevention — yet fire counts are exactly the evidence used to decide what to delete.
  - Dozens of items sit on six-month review clocks, far more than the one forcer-off experiment the spec can run per model generation.
  - As written, the process will mass-rubber-stamp everything or mass-delete working guards. It needs outcome-side metrics (e.g., defect-class recurrence) and tiered review classes.
- **F5. The spec credits the blind author with catches that actually require reading code.** (MED, confirmed) Every recorded catch in the green-but-wrong class came from a reviewer reading the actual code. That is the one thing the blind author can't see. So internal-state corruption invisible at the interface would pass right by it.
  - Whether the blind author adds real value beyond the existing plan-plus-adversary setup is still just a hypothesis.
  - The spec should state it as one, tie lane-policy status to the blind-author-cheat simulation, and declare the blind author's tier.
- **F6. Raising the autonomy dial reduces the very data that would argue against raising it.** (MED, confirmed) Escaped defects surface through human contact with the work, and higher autonomy means less of that contact per unit of work. So as autonomy rises, found-escape counts fall — not because there are fewer escapes, but because fewer humans are looking. This is a one-way ratchet unless the count is normalized against exposure, e.g. drives per unit of delivered work.
- **F7. The patch lane lets through the exact type of defect that has caused the most damage.** (MED, confirmed) The historical record's own worst-defect example is a tiny, gate-passing, build-killing change. Under the ties-lighter rule, exactly this kind of change routes to the no-review patch lane. And the lane audit, which checks only size and blast radius, scores the routing as correct. Needs a stronger router, or sampled async review of landed patches.
- **F8. The Record was validated on the same repos it was built from.** (MED, confirmed) The checks were tuned until the two repos the standard was derived from scored as expected — an in-sample test with a sample size of two.
  - The cold reader's "proven" claim rests on a sample size of one, with an unmeasured false-positive rate — needs held-out calibration documents that weren't used to build the standard.
- **F9. The blind author's fix loop, as specified, would expose it to the code bodies it's supposed to be blind to.** (MED, corroborated) Its test suite has to compile and run. But harness layout, fixtures, and dependency injection sit outside its three allowed inputs. Compile errors and assertion diffs echo the code back anyway.
  - The simulation's transcript-purity rule is treated as sealed spec, but the fix-loop's visibility rules are still an open item: settled and unsettled at once.
  - Needs a laundering layer: the driver runs the suite, failures come back rephrased in design/plan terms rather than code, and any crossing gets journaled.
- **F10. The teach-back has no sunset review and no way to check it's actually working.** (LOW, confirmed) The teach-back is the one major mechanism with no sunset class and no falsifiable check. Its metric — how many decisions it covered — can stay green even if it teaches the owner nothing.
- **F11. UI pairing was scaled up in a way that contradicts the spec's own evidence on cost.** (MED, confirmed) The remedy the historical record actually supports is milestone-headline drives. But pairing scales the flakiest test class to cover every user-facing case, with no stated cost. That builds in repeat-waiver fatigue by construction. Consider scoping pairing to headline cases per milestone, pricing it against a flake budget, and keeping UI twins out of per-slice mutation runs.

## G. Real limits on who can adopt this, left unstated

- **G1. The spec depends on Claude Code specifically, but never says so.** (HIGH, confirmed) Hooks, in-session subagents, session-ID stamping, and using transcripts as an archive are all load-bearing parts of the design, and all assume Claude Code specifically. No file states this as a host requirement, and no degraded mode is defined for any other host.
- **G2. The single-owner assumption is baked in everywhere but never stated as a decision.** (HIGH, corroborated ×3) Every mechanism hard-codes exactly one owner: identity-free seals, one Queue, one registry, one stream of judgment. Once a second person is involved, there's no way to attribute who accepted what. Needs an explicit scope decision either way — and if single-owner is the answer, the spec should say what the handoff artifact is when that changes (see E9).
- **G3. The spec has no way to handle libraries or SDKs.** (HIGH, confirmed) No topology is defined for a package or SDK, where the front door is an API consumed by other code, not a UI.
  - The drive artifact is a hard mechanical gate with no defined meaning here, leaving a library author two options: fake the evidence, or never get a seal.
  - Needs a library topology — install-from-package, import, and a consumer-fixture round trip — plus a definition of "drive" for a library.
- **G4. The spec has no answer for repos with more than one topology, like monorepos.** (MED, confirmed) The manifest declares only a single profile per repo, though most real repos are several at once. "Web" appears in an open item, but not in the canonical list of four topologies. For a monorepo, the spec never defines what counts as "the project" — how many registry entries, manifests, and standards sheets it should have.
- **G5. The spec has no stated policy on which platforms it supports.** (MED, confirmed) "macOS first" only appears inside an open item, not as a stated policy. Adopters on Linux or Windows are left indefinitely with the fallback mode, which is itself broken (see B8), with no statement of intent about whether that will change.
- **G6. The brownfield day-one plan requires a step it also says shouldn't happen yet.** (MED, confirmed) Deletion tests are listed under "installs immediately, no sockets," meaning they should work before any sockets are mapped — but they require executing the mapped test socket, which contradicts that. Separately, the day-one ratchet baseline is set before the adoption-seal rules exist that would count against it. This ordering needs one honest, careful pass.
- **G7. Nobody is named as responsible for extending the battery to new stacks.** (LOW, confirmed) Marker filtering, run-log parsing, and interface extraction all exist as real code, but only for six stacks. The spec asserts "every stack's test runner supports it," without saying who builds the adapter when a seventh stack shows up.

## Convergence notes

The strongest signal comes from findings multiple blind reviewers reached independently. Stale dispatch arithmetic: 3 reviewers plus the driver. Flakes: 4 reviewers. Dev-mode leakage, revert/abort, and the one-human scope problem: 3 reviewers each. The sunset regime's evidence problem: 2 reviewers, from opposite directions. Squash-merge fragility and the markdown-fallback hole: 2 reviewers each.

The driver's own blind pass raised ten candidate findings; nine were independently corroborated by other reviewers. One was wrong: the driver thought the spec banned feature flags. In fact the spec is simply silent on them — and the reviewers correctly identified that silence as its own gap (see E4).
