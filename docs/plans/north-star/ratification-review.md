# Ratification review — adversarial findings register

**What this is.** Seven reviewers read the full nine-file spec at commit `16c5ce4` (2026-08-06). Each reviewer worked blind, with fresh context, and used one lens: internal consistency, reasoning flaws, operational failure modes, cost honesty, cold adoption, security and privacy, or life-cycle coverage. The driver ran its own blind pass first, before reading any of the reviewers' work. Then the driver triaged every finding against the spec text. This file is the curated register. The full agent outputs live in the session transcripts.

**This file is evidence, not spec.** Nothing here changes the spec just by existing. Each finding still needs an owner decision: amend the spec, add the finding to open items, scope it out explicitly, or dismiss it with a reason.

**Status tags.** `confirmed` means the driver checked the quotes and the logic against the spec text. `corroborated` means two or more reviewers found the same issue independently, while working blind. `plausible` means the finding is credible but not independently verified — the owner should judge it.

**Disposition (2026-08-06).** The owner directed a full fold-in of these findings. One ruling reshaped cluster A: tokens are the scarce resource, not dispatches. Small dispatches are fine; total token consumption is the real budget. The owner also added one requirement: the framework must not bind to a single vendor. It needs host portability, with OpenAI-compatible hosts as the minimum bar. The fold-in landed in four commits: `91aefb5` (clusters A and F: token economics, honesty reframes), `ed15797` (cluster B: contradictions), `bdd974b` (clusters C and D: evidence-layer git reality, security floor), and `1d25731` (clusters E and G: operational life, the adoption boundary, the host adapter contract). Security defaults, the flake/release/backward-move machinery, and the single-owner scope statement were driver calls made under that mandate. They were flagged in chat as veto points.

## A. The cost estimates are stale and mix incompatible units

- **A1. The dispatch savings estimate is wrong under the new definitions.** (HIGH, corroborated ×3) loop.md and changes.md still claim "~20 frontier dispatches (from ~35)." But this compares two different things. The old number (~35) was a measured total of all dispatches. The new number (~20) is an ideal count of frontier dispatches only. It also leaves out roles added later by amendment: the blind test author, the capsule writer, the standards cleanup pass, and the design-seal adversary. When you recount using the same method for both, a complex bet with 3 milestones and 8 slices costs about 50–60 total dispatches. That is more than today, not less. The blind author, capsule writer, and cleanup pass also have no stated tier. index.md itself says leaving a role's tier off is an error.
- **A2. The old number includes rework; the new number does not.** (HIGH, confirmed) The old figure of 35–45 dispatches includes bounce rounds — rework cycles. The new target of 20 assumes one clean pass, with no rework. But the blind author is designed to *increase* bounce rounds. Elsewhere the spec prices each bounce round at up to 41% of a build.
- **A3. Complex slices now run through five or six sequential stages.** (MED, corroborated) The chain now runs: build, then handoff/extraction, then blind authoring, then triage, then battery, then adversary, then capsule. Each stage starts with fresh context. Unattended throughput is limited by how long one slice takes, and that time roughly doubles under this chain. No elapsed-time budget exists anywhere in the spec, and the journal does not record how long any of this takes.
- **A4. The "short brief" the blind author reads is actually design-sized.** (MED, confirmed) On the complex lane, the blind author's input is the full sealed design walk, copied into about 8 dispatches per bet. Separately, the milestone-sum adversary must hold the assembled diff, the design, the tests, and the code all at once, and write new tests, within a cap of "three reads, no more." This is the largest context window anywhere in the system. The spec presents it as a reduction.
- **A5. The "10–15 moments" figure counts pauses, not the decisions inside them.** (MED, confirmed) The spec's headline claim — "10–15 moments → the seals" — compares a count of pauses to a count of decisions, as if they were the same thing. One bet-close sitting still contains about 15–25 separate decisions: 8 capsules, a row-by-row board read, the drive, the teach-back, batched ratifications, doc approvals, and the merge go-ahead. The Map's own decision-budget instrument counts decisions. The headline number should too.
- **A6. The driver's own token spend is missing from the spend accounting.** (LOW, confirmed) The spend-by-role accounting only covers dispatches. The driver itself is not a dispatch, but it assembles every brief, inspects every diff, triages every finding, and runs every teach-back. This is likely the most expensive part of the system, and it is structurally left out of the "sorted column" of spend.
- **A7. The new machinery built to replace prose has no maintenance-cost check.** (MED, plausible) The spec measures the word count it cuts down to the thousand. But the roughly 31 new components on the build list — the daemon, the journal, board derivation, the battery, UI-driver toolchains, the update engine, the sim rig — have no check on their maintenance cost. At one-person scale, upkeep is the documented historic failure mode: 384 commits of it.

## B. Internal contradictions, mostly caused by the order amendments were made in

- **B1. The spec contradicts itself on whether tests come before or after the code.** (HIGH, confirmed) standards.md states the rule plainly: "Tests are written first and observed failing before the implementation exists." But proof.md now has the complex lane's accepting test suites written *after* handoff — and elsewhere claims tests are "authored at decomposition, committed red, exactly as today." That is three different moments when tests get written: decomposition headline proofs, blind suites written after handoff, and auditor extensions. The spec never reconciles these into one consistent story. Read literally, the tests-first rule cancels out the blind author.
- **B2. Goal 11's autonomy-scaling rule has no defined computation behind it.** (HIGH, confirmed) Goal 11 says: "Autonomy scales with verification… probe coverage of the touched area, not the task's label." But the dial's actual inputs are owner choice, per-lane defaults — which is exactly a task label — and sensitive paths. doors.md asserts that this computation happens, but no file defines it or connects it to the dial.
- **B3. The rule that nobody writes the journal contradicts dev mode's own driver-written event.** (MED, confirmed) The spec states "No human or agent ever writes it" about the journal. But the driver-written method-friction event appears in that very same sentence's list of journal events.
- **B4. The stopping rule claims to be a closed list of five, then adds a sixth item.** (MED, confirmed) The spec introduces the stopping rule with "A genuine stop is only:" and then lists five items. Two bullets later, it declares an unaccepted-contract dependency to also be a genuine stop — a sixth item outside the closed list. An implementation that follows the list mechanically would miss it.
- **B5. The term "open finding" is used with two different, conflicting meanings.** (MED, confirmed) One passage says "A slice cannot close over an open finding." Another refers to "open deferred findings" that show up on the known-gaps view precisely because slices closed past them. The spec implies a finding-state model where "open" blocks closing but "deferred" or "dismissed" do not — but it never states this model directly.
- **B6. The module graph has a second real consumer that its own retention test ignores.** (MED, confirmed) changes.md says the module graph has "its one consumer," the ripple caller list, and that it should be deleted if unused. But record.md still relies on the module graph — it names it as the staleness check's way of reaching indirect drift. So the retention test, following changes.md, could delete a mechanism that the Record itself depends on.
- **B7. The spec credits the wrong system for catching a schema hole that was missed twice.** (MED, confirmed) index.md credits the catch to "magpie's own mechanical gate." But evidence.md and proof.md both place it in staycurrent instead — the loader/gate story behind ADR 0006. This is a factual error, and it sits in the ratification headline.
- **B8. Nothing actually produces the markdown pages the no-daemon fallback promises.** (MED, corroborated ×2) The spec claims "The same pages exist as committed markdown" when the daemon isn't running. But the six-writes deletion removed the exact mechanism that used to commit those pages, and rendering moved into the daemon instead. As specified, what's left without the daemon is raw ledgers, not readable pages.
- **B9. The tower is defined as read-only, but the Queue needs to write somewhere.** (LOW, confirmed) Queue outcomes produce ledger writes and filed issues. But the only named server, the tower, is read-only. No file says where those writes actually happen.

## C. The evidence layer does not hold up against how git actually works

- **C1. The journal is tied to git history, which is not append-only in practice.** (HIGH, confirmed) Most journal events have no commit to attach to — dial changes, triages, teach-backs, and every red run on a reworked or bounced slice. Yet the spec says "a check with no journal lines is a check that never ran." When parallel bets append to one file, every merge conflicts. Rebases duplicate lines. Reverts delete lines from what is supposed to be an "append-only" record. Under normal git use, the evidence layer that governance, sunset, and spend all depend on gets corrupted. Fix direction: store the journal outside the work DAG — for example, in git notes or refs, or in an owner-level log keyed by commit SHA and session.
- **C2. Squash merges and branch teardown can erase the history the views depend on.** (HIGH, corroborated ×2) A single squash merge collapses a whole bet into one commit with no trailers. This erases the entire derivation, so the bet renders as an unlaned bypass. Seal tags point at commits that leave history once the branch is torn down. The spec's "frozen forever" views are re-derived from refs that teardown removes, and no mechanism is stated to persist them first. There is also an adoption problem here: repos with protected branches, or that require PRs with squash merges, cannot grant the git contract the spec assumes. doors.md never names this as a precondition.
- **C3. Unattended runs have no limits on retries, spend, or detecting a dead run.** (HIGH, confirmed) There is no retry ceiling and no per-slice spend ceiling for a genuinely red row. There is no way to detect a dead run — quota exhaustion, a crash, or the machine going to sleep, all cases where the worker's changes are deliberately left unstaged. The push channel for genuine stops is "optional and deliberately undecided," even though dial settings at bet level or higher depend on it.
- **C4. The parallel-run design does not address the lock-contention problem it names.** (MED, confirmed) evidence.md describes a 62% worktree index-lock failure rate as "a warning the parallel design must engineer around." But no file actually engineers around it. Fix direction: use one serialized git writer per repo.
- **C5. Tag pushes are missing from the backup process, so seals can go unseen on other machines.** (MED, plausible) Branch pushes are automatic, but tag pushes are never mentioned anywhere in the spec. A seal granted on one machine stays invisible to another machine's Map, Queue, and `verify`. The tower reads local clones, and nothing indicates when a local clone is behind the remote.
- **C6. A stricter existing check, not just a new one, can turn a live board red mid-run.** (LOW, confirmed) The ratchet-arrival mechanism only covers checks that are newly *added*. If an existing check becomes stricter instead, it can turn previously claimed-done proofs red again, stopping every in-flight unattended run. This reproduces, inside the spec's own mechanism, exactly the failure mode it warns about elsewhere: "a release that turns projects red."
- **C7. Hook decay goes undetected, even though the spec says hooks don't decay.** (LOW, confirmed) The spec says "Hooks do not [decay]." In practice they do — host updates, overwritten settings, and fresh clones can all break them. Hook firings are not journal events, so nothing notices when a hook stops surfacing information. The system quietly degrades back to the old invisible model it was built to replace.

## D. Security and privacy holes in the framework's own infrastructure

- **D1. The tower gathers every project's data at one address with no authentication.** (HIGH, confirmed) The tower holds every registered project's plans, ledgers, and in-flight state, all at one stable local address. The words "authentication," "binding," and "origin" appear nowhere in the spec. Any other user or process on the same machine can read the whole portfolio — and, through browser tricks, so can a remote web page. The spec's open item about the tower covers its lifecycle but says nothing about authentication.
- **D2. Dev mode can leak journal data and project details into a public repo.** (HIGH, corroborated ×3) Issues filed in the public framework repo carry journal lines, project file paths, and session IDs. There is no redaction step. The auto-file option publishes these issues without a human ever looking at them first. And "maintainer" status is just a local flag — any adopter can set it themselves.
- **D3. Debug mode can commit secrets to git and push them off-machine.** (HIGH, confirmed) Debug mode widens journal lines to include full check output. That output can include secrets-scan results and real-infrastructure logs. This gets committed into git history and immediately pushed off-machine as a backup.
- **D4. The update engine can push unsigned code into every registered repo's hooks and CI.** (HIGH, confirmed) Hooks run at the start of every session, and CI stanzas auto-reconcile, both by design with no human review. There is no signing, no provenance tracking, and no attestation anywhere in this process. The package-hash check only confirms what got installed — it does not verify that what got installed is safe. One compromised release becomes silent code execution across every registered project and its CI.
- **D5. The permission model for unattended runs is only written down, not enforced.** (MED, confirmed) The spec calls for "a *stated* permission model." But the spec's own doctrine elsewhere is that prose alone loses — it doesn't hold up. Nothing here actually enforces path allowlists, pins push remotes to specific targets, scopes credentials, or bounds network access during multi-day runs. The stopping rule only fires if the agent itself decides its own action counts as crossing a boundary.
- **D6. The agents being audited can also alter the evidence that audits them.** (MED, confirmed) The journal, the ledgers, and the seal tags are just plain files and git tags, in a repo the agents themselves have full write access to. "Append-only" and "the only way it moves forward" are conventions, not enforced rules. Fix direction: a hash-chained journal, signed seals, and a chain that `verify` actually checks.
- **D7. Probes run an untrusted repo's own commands before any audit happens.** (MED, confirmed) The spec declares a brownfield repo's content untrusted for *reading*. But probes run the repo's own test and build commands the moment sockets are mapped — before any seal or dependency audit happens.
- **D8. The tower can render untrusted, agent-written docs with no isolation between projects.** (MED, plausible) Markdown written by agents, or seeded from a brownfield repo, gets rendered by the tower. No sanitization, content security policy, or isolation is specified. One injected document becomes stored cross-site scripting, with read access to every project's pages.
- **D9. Projects get registered automatically, with no opt-out for private work.** (LOW, confirmed) `init` and `update` register a project unconditionally. There is no per-project flag to keep a project local-only or excluded — something NDA-bound work would need.

## E. What happens to software after it ships — the spec's blind side

- **E1. There is no fast path for emergencies, and no way for production signals to reach the system.** (HIGH, confirmed) Even the fastest lane still runs the full battery. An unrelated red row at 2am still requires a full sealed-waiver process before anyone can act. Nothing in the system reads the observability data the standards require projects to ship — no alert and no user report ever reaches the Queue or the Map. The only thing that catches problems after shipping is "the owner, in use."
- **E2. There is no way to formally revert or abort a shipped change.** (HIGH, corroborated ×3) Revert only exists as a capsule *metric* — it is never a real mechanism. If a capability is un-shipped, the permanent suite, the manifest (`add-capability` has no matching remove), the Map (which says "forever"), and the Record all keep asserting that the capability still exists. Mid-flight withdrawal — which the historical record shows actually happening — has no defined end state. It leaves stalled-forever lines, known-gaps entries that can never be discharged, and branch deletions that destroy the evidence. Fix direction: make "reverted" and "withdrawn" first-class states, each with a defined cascade of effects.
- **E3. The spec has no concept of a flaky test.** (HIGH, corroborated ×4) There is no concept anywhere of retrying a test, quarantining it, or tracking its flake rate. Meanwhile the board treats red and green as ground truth, one red row counts as a genuine stop even at night, and the pairing rule made the flakiest class of test the headline row of every user-facing proof. Every flake has to route through a full sealed human waiver — which builds in the exact override-fatigue problem the spec documents elsewhere.
- **E4. The spec's proofs stop at the merge and never reach real deployment.** (HIGH, confirmed) The spec has no product versioning, no changelog, no release channel, no deploy environment, and no staged rollout anywhere. It never mentions feature flags at all — the ban on them lives in the old delivery contract, not this one — so there is no mechanism for partial exposure and no stated position on whether one should exist. The front door proves that the build works, not that it was deployed. Whether something actually shipped to real users sits outside every proof the spec defines.
- **E5. Performance is named as a baseline but has no row of its own.** (MED, confirmed) standards.md announces "security, privacy, accessibility, and performance baselines," then only lists rows for three of the four — performance is missing. The framework's founding failure case included a 5–10× slowdown that still passed as green. Under this spec, it still would.
- **E6. A dependency vulnerability is detected but has no defined response.** (MED, confirmed) A red dependency-audit row has no assigned lane, no owner, and no cadence for handling it. A new CVE turns the battery red for slices that have nothing to do with it, and the spec has no "the world changed" state that is distinct from "you broke it."
- **E7. Data migrations and backfills are not actually proved.** (MED, confirmed) The spec's "migration apply" proof only covers a fresh environment. There is no proof for reversing a migration, no duration category for backfills that take hours, and no rule for where fixtures built from production data come from. Fixtures are policed for being too fake, but never for being too close to real production data.
- **E8. Nothing bounds the system's long-term growth in stored evidence.** (MED, confirmed) The journal, the archives, the frozen views, and the delete-nothing test suite all grow without bound. The cost of the per-slice deletion test scales with the size of the suite. By year three, battery latency will quietly break the patch lane's promise of being "checks-only cheap" — and slow verification is the documented trigger that makes people bypass the process. Nothing in the spec sets a runtime budget, tiering scheme, or segmentation to prevent this.
- **E9. The spec has no plan for what happens if the owner changes.** (MED, plausible) Seals are identity-free tags stored in one laptop's registry. There is no handoff artifact, no model for a second person joining, and no onboarding process for a new method maintainer. This would be fine as an explicit scope decision — it is a problem only because the spec is silent about it instead. (See G2.)

## F. Reasoning flaws in the evidence story

- **F1. A keep decision is justified using evidence that no longer exists.** (HIGH, confirmed) The spec claims "Per-slice correctness review was never observed to rubber-stamp." But the raw review outputs were deleted for 21 of 23 bets, and attribution was never filled in. That means the miss rate is genuinely unknowable. Keeping per-slice review may well be the right call as a starting assumption — but the spec presents it as a measured fact, which it is not.
- **F2. Only one of three lens changes was actually backed by evidence.** (HIGH, confirmed) The spec claims its lens split is evidence-based, but only the honesty audit was actually measured. The edge-case lens — which has named, real catches within a single slice, one of them build-killing — and the coverage lens — which has repeated real findings — were both demoted anyway, on the unmeasured claim that moving to milestone-close "gives them more to bite on." This needs an honest label acknowledging it's unproven, plus a clause to roll it back if those problems recur.
- **F3. Clean escalation reports can't be trusted as proof the channel works.** (HIGH, confirmed) The escalation contract exists in the first place because cheap models can't reliably judge their own limits. That means a dozen reports saying "BLOCKING CONCERN: none" cannot be read as proof the channel works — a model that can't judge its own limits also can't reliably report when it's hit one. The rate of missed escalations is unknowable, yet the tier policy tunes itself on this flattering but unverified signal. This needs a way to measure *missed* escalations directly — for example, having the adversary tag findings that the worker should have escalated but didn't.
- **F4. The sunset process can't tell prevention from irrelevance, and has too many items to review.** (HIGH, corroborated ×2) The spec itself acknowledges, in the case of linters, that zero firings looks identical to perfect prevention. Yet fire counts are exactly the evidence used to decide what to delete. On top of that, dozens of items are on six-month review clocks, far more than the one forcer-off experiment the spec can run per model generation. As written, this process will either mass-rubber-stamp everything or mass-delete guards that are actually working. It needs outcome-side metrics — like tracking whether a defect class recurs — and tiered review classes so not everything is reviewed the same way.
- **F5. The spec credits the blind author with catches that actually require reading code.** (MED, confirmed) Every recorded catch in the green-but-wrong class came from a reviewer reading the actual code — which is the one thing the blind author is not allowed to see. Internal-state corruption that's invisible at the interface would pass right by it. Whether the blind author adds real value beyond the existing plan-plus-adversary setup is still just a hypothesis. The spec should state it as a hypothesis, make lane-policy status depend on the blind-author-cheat simulation, and declare the blind author's tier.
- **F6. Raising the autonomy dial reduces the very data that would argue against raising it.** (MED, confirmed) Escaped defects are found through human contact with the work. Higher autonomy rungs mean less human contact per unit of work. So as autonomy rises, the count of found escapes falls — not necessarily because there are fewer escapes, but because fewer humans are looking. This becomes a one-way ratchet unless the count is normalized against exposure, for example drives per unit of delivered work.
- **F7. The patch lane lets through the exact type of defect that has caused the most damage.** (MED, confirmed) The historical record's own example of a bad defect is a tiny, gate-passing, build-killing change. Under the ties-lighter rule, exactly this kind of change routes to the patch lane, which has no review. The lane audit, which only checks size and blast radius, scores this routing as correct. This needs either a stronger router or sampled async review of patches after they land.
- **F8. The Record was validated on the same repos it was built from.** (MED, confirmed) The checks were tuned until the two repos the standard was derived from scored as expected. That only validates the standard against the same two repos it was built from — an in-sample test with a sample size of two. The cold reader's claim of being "proven" rests on a sample size of one, with an unmeasured rate of false-positive flags. This needs held-out calibration documents that weren't used to build the standard.
- **F9. The blind author's fix loop, as specified, would expose it to the code bodies it's supposed to be blind to.** (MED, corroborated) The test suite the blind author writes has to actually compile and run. But harness layout, fixtures, and dependency injection are all outside the three inputs the blind author is allowed to see. Compile errors and assertion diffs echo the code bodies back to it anyway. The simulation's rule about keeping transcripts pure is treated as sealed spec, while the fix-loop's visibility rules are still an open item — so the spec claims something is settled that the execution plan still has to work out. This needs a defined laundering layer: the driver runs the suite, failures come back rephrased in terms of the design and plan rather than the code, and any crossing gets journaled.
- **F10. The teach-back has no sunset review and no way to check it's actually working.** (LOW, confirmed) The teach-back is the one major mechanism with no sunset class and no falsifiable check. Its metric — how many decisions it covered — can stay green even if it teaches the owner nothing at all.
- **F11. UI pairing was scaled up in a way that contradicts the spec's own evidence on cost.** (MED, confirmed) The remedy the historical record actually supports is milestone-headline drives. But pairing scales the flakiest test class up to cover every user-facing case, with no stated cost. This builds in repeat-waiver fatigue by construction. Consider scoping pairing to headline cases per milestone, or pricing it against a flake budget, and keeping UI twins out of per-slice mutation runs.

## G. Real limits on who can adopt this, left unstated

- **G1. The spec depends on Claude Code specifically, but never says so.** (HIGH, confirmed) Hooks, in-session subagents, session-ID stamping, and using transcripts as an archive are all load-bearing parts of the design. All of them assume Claude Code specifically. No file states this as a host requirement, and no degraded mode is defined for running on any other host.
- **G2. The single-owner assumption is baked in everywhere but never stated as a decision.** (HIGH, corroborated ×3) Every mechanism in the spec hard-codes exactly one owner: identity-free seals, one Queue, one registry, one stream of judgment. The moment a second person is involved, there's no way to attribute who accepted what. This needs an explicit scope decision, made either way. If single-owner is the answer, the spec should also say what the handoff artifact is when that changes (see E9).
- **G3. The spec has no way to handle libraries or SDKs.** (HIGH, confirmed) The spec has no topology defined for a package or SDK, where the front door is an API consumed by other code rather than a UI. The drive artifact is a hard mechanical gate, but it has no defined meaning for this case. A library author is left with only two options: fake the evidence, or never get a seal. This needs a library topology — install-from-package, import, and a consumer-fixture round trip — plus a definition of what "drive" means for a library.
- **G4. The spec has no answer for repos with more than one topology, like monorepos.** (MED, confirmed) The manifest only declares a single profile per repo, but most real repos are several profiles at once. "Web" appears in an open item, but not in the canonical list of four topologies. And for a monorepo, the spec never defines what counts as "the project" — how many registry entries, manifests, and standards sheets it should have.
- **G5. The spec has no stated policy on which platforms it supports.** (MED, confirmed) "macOS first" only appears inside an open item, not as a stated policy. Adopters on Linux or Windows are left indefinitely with the fallback mode, which is itself broken (see B8), and there's no statement of intent about whether that will ever change.
- **G6. The brownfield day-one plan requires a step it also says shouldn't happen yet.** (MED, confirmed) Deletion tests are listed under "installs immediately, no sockets" — meaning they should work before any sockets are mapped. But deletion tests actually require executing the mapped test socket, which contradicts that. Separately, the day-one ratchet baseline is set before the adoption-seal rules exist that would count against it. This ordering needs one honest, careful pass.
- **G7. Nobody is named as responsible for extending the battery to new stacks.** (LOW, confirmed) Marker filtering, run-log parsing, and interface extraction all exist as real code, but only for six stacks. The spec asserts that "every stack's test runner supports it," without saying who builds the adapter when a seventh stack shows up.

## Convergence notes

The strongest signal comes from findings that multiple blind reviewers reached independently. The stale dispatch arithmetic was found by 3 reviewers plus the driver. Flakes were found by 4 reviewers. Dev-mode leakage, revert/abort, and the one-human scope problem were each found by 3 reviewers. The sunset regime's evidence problem was found by 2 reviewers, approaching it from opposite directions. Squash-merge fragility and the markdown-fallback hole were each found by 2 reviewers.

The driver's own blind pass raised ten candidate findings. Nine of these were independently corroborated by other reviewers. One was wrong: the driver thought the spec banned feature flags. In fact the spec is simply silent on feature flags — and the reviewers correctly identified that silence as its own gap (see E4).

## Suggested disposition classes (owner decides)

1. **Mechanical amendments before ratification.** These are the confirmed contradictions and stale numbers: A1–A6, B1–B9, C6, E5, the relabeling called for in F1–F2, and the misattribution in B7.
2. **Design decisions the owner must make.** These cover security posture (D1–D9), evidence-layer storage (C1–C5), operational-life additions (E1–E4, E6–E8), the blind-author fix-loop and pairing scope (F9, F11), and adoption boundary statements (G1–G6).
3. **Honesty reframes.** These restate evidence claims as priors or hypotheses, each with a named instrument that could settle them: F3–F8, F10.
