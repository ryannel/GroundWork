## Useful source paths and field lineage

For registration, `payload.paymentSessionId` selects existing RETRY jobs through `params.paymentSessionId`. An existing job returns 208 without creating/saving another job; absent results proceed to config selection and a new UUID job. Multiple matching jobs throw `SchedulerException` carrying 409; this field alone is **not** modelled as an HTTP 409 response. The known local advice maps `ConfigNotFoundException` to 404; imported/general exception behaviour remains partial.

The new job copies retry state into `params.lastRetryState`, plus country, cart line, payment-session ID, recurring-charge ID and retry strategy/expiry. It starts PENDING/RETRY with runCount zero. Initial scheduling calls the strategy with non-null current time; FixedRateStrategy therefore takes its period branch rather than its null-time initial-delay branch. Local interval and cron declarations are retained, with imported cron runtime/default timezone details partial. The duplicate lookup and subsequent generated-ID save are separate calls without a proved unique payment-session constraint or shared transaction.

`RegisterRetryResponse.fromJob` maps jobId→jobId, nextRunAt→nextRunAt, lastRunAt→lastRunFinishedAt, runCount→retryCount and status→jobStatus. The source returned factory result is distinct from the mapped DTO argument and the original Job. The imported SuccessResponse/BaseResponse outer fields and effective JSON remain partial; the inner DTO is not labelled as the entire response envelope. `RetryApiService` discards the save method's returned mapper copy and returns its original mutable Job; normal Mongo save acknowledgement is recorded separately.

For polling, skip-first-run returns before locking. Otherwise successful acquisition gates the cycle; an unavailable lock avoids job execution. The query selects the first PENDING job whose nextRunAt is earlier than the current poll time, ascending by nextRunAt, page size one. Eligibility compares **runCount** with maxRuns. IN_PROGRESS is saved before the RETRY executor calls the payment API using **stored `job.params.paymentSessionId`**.

The response is an imported `SuccessResponse<RetryPaymentSessionDto>`, represented by a partial outer source getter projection containing a distinct partial DTO. The retry path unwraps getData, chooses the history element with maximum attemptedAt and copies its retryState. Empty history throws; states other than ON_SCHEDULE/NEEDS_CARD_UPDATE mark the job completed. Those two states reselect config and set PENDING; a config-ID change resets runCount. The base executor subsequently increments runCount and totalRunCount, then persists post-run scheduling. Completion checks **totalRunCount**, expiry or existing COMPLETED state. The counter distinction is a source-backed claim, not normalised away.

Notification construction reads IDs, retryStrategy and lastRecurringChargeState from the payment API response; `nextRetryAt` is overridden from the current mutable job's nextRunAt. The Kafka **key** independently comes from stored `context.job.params.recurringChargeId`; equality with the response's recurringChargeId is not assumed. Metadata uses a UUID, epoch seconds, correlation ID and imported source/type/version constants. The constructed generic Event retains separate payload/metadata shapes. Effective Kafka JSON fields and imported inherited fields are unknown, so the wire shape is deliberately partial rather than guessed from source names.

Value queries preserve these projection instructions and conservative aggregate origins. A query through RetryContext can include both its job and response origins; it is not a field-sensitive proof that the response supplies the key. The explicit source access path and transformation establish that distinction. Source snippets, not path feasibility or runtime observations, support the branch statements.

## Acknowledgement and partial closure

The sequence is payment retry → synchronous job persistence → local Kafka attempt. There is no proved shared transaction or outbox across them. A crash can separate the payment effect from the job save; a later publication failure can leave the saved state without a delivered notification. The source marks failures in per-job processing ERROR and saves them, refreshing the lock in the source finally block. Poll release is another finally action. Imported repository/HTTP failures, failures within finally blocks and some typed exception propagation remain partial; the graph does not claim exhaustive failure coverage.

KafkaProducer returns void after registering `whenComplete`. `waitsFor: none`, `awaited: false` and a `publication_attempt` milestone preserve this boundary. No broker persistence, downstream completion, delivery guarantee, retry/deduplication policy or offset commitment is invented. The separate callback checks whether exception is null and logs success/failure; its source declares no job write or retry. A source-backed association claim links registration and captured inputs to that graph. Native continuation queries deliberately do not treat it as a Kafka subscription/handoff. Callback executor/timing remains an imported runtime gap.

Lock code inserts, checks count, refreshes expiry and deletes by name/instance. It expects uniqueness/TTL behaviour, but no index creation proof was found and source auto-index creation is false. Lock insertion and count verification are separate; no distributed lock safety guarantee is claimed. The native lock interactions summarise those method-level operations and conditions; they do not prove atomicity or complete affected-row semantics.
