# Customer CRM Synchronizer independent source notes

The source host imports shared EcomWebAppConfiguration and excludes Spring Security autoconfiguration; this does not prove unauthenticated deployment. Three declared REST methods use class /v1/ plus method templates, required VCC-Remote-System header which their bodies do not use, and role annotations. Two PUT methods invoke CDB sync with create=true and return SuccessResponse.ok(null,correlationId), not the returned CdbSyncResult. The deprecated consumer lookup uses another role and returns projected CdbConsumerData. Imported response envelope/validation/security/runtime dispatch stay separate authorities.

Three Kafka registrations remain distinct. CustomerEventConsumer and CustomerEventOMConsumer consume the same literal app5541-customer-events with different configured groups; only the CDB sync consumer has the self-origin azureAppId remoteSystem suppression. Both skip CUSTOMER_ARCHIVED but metadata is dereferenced earlier, so null guard does not cover initial correlation access. Customer change passes create=false; CdbSyncEventConsumer passes true and only logs orderId. All deserialisation and initial metadata/payload work is outside the CustomerNotFound catches. Other failures propagate to imported error handling. OM consumer sends CUSTOMER_UPDATE category; successful CDB-ID patch later sends CRM_UPDATE.

CustomerSyncService gets remote customer, synchronously processes individuals, derives signatoryCdbId from first SIGNATORY actor with updated-ID fallback, then corporate entities, then PATCHes changed IDs. Prior remote CDB updates may survive later actor/patch/OM failure; there is no source local database, broker publication, transaction or compensation. The CDB response new-null ID comparison treats null as unchanged. Individual skip: create=false and absent cdbId, US sole PAYER, sole APPROVER without surname. Corporate skip: create=false absent cdbId, roles absent/no SOLD_TO, or existing fleetAccountId. Stream callbacks/overloads must resolve actual source targets.

CDB client qualifier cdb establishes POST /consumer with actual CreateOrUpdateRequest, decoding CdbResponse then responseDetails and rejecting missing body/details. ResourceAccess escapes, HTTP400 parses responseDetails.nounFailure.errorMessage descriptions then root errorMessage/raw fallback; description containing LOCKED/MODIFIED becomes CdbConsumerLockedException, other rejected data CdbDataRejectedException. Retryable includes ResourceAccess and locked, excludes HttpTimeoutException and uses configured retry counts/delay. EnableResilientMethods is declared; imported retry interception/timing/wrapping remains unresolved, not fabricated Java loops. GET /consumer/alternativeIds/{alternativeId}?type={idType} sends actual volvoId and ALT_ID_MY_VOLVO_ID, decodes whole CdbConsumerByVolvoIdResponse then nullable details; CdbConsumerService subsequently dereferences consumer without a top-level null guard.

Customer client qualifier customer-service GET /v1/customers/{customerId} retains whole imported SuccessResponse<Customer> then getData and empty-body guard; 404 maps CustomerNotFoundException. PATCH samepath sends PatchCustomerRequest then toBodilessEntity. Request mapper forwards only isUpdated actors with id/cdbId/cdbTcId. CustomerService only PATCHes and then calls OM when either changed list nonempty. OM qualifier order-manager POST /internal/ordermanager/v1/orders/customer-update-event/{customerId} sends category record; ResourceAccess rethrows, 404 and409 are logged/swallowed, other RestClient errors wrap. The source comment's remote duplicate-event explanation is not verified downstream implementation. OM enabled config defaults true, but effective environment is unresolved.

CDB request construction sets brand VCC, component OM, authorizationId CustMgr, bodId actual correlationId and nested consumer. Imported model setters are known mutations with explicit operands, not fluent returned values. Consumer construction separately sets info/alternativeIDs/relatedconsumer/person/organization/addresses/contact/email and conditional vehicle relation. Person uses DOB/firstName/gender/spinPersonNumber/surname and only TITLE_-prefixed title. Organization only SOLD_TO and regName/regNumber/vatNumber/displayName. Vehicle requires nonblank VIN and nonnull handoverDate; individual SIGNATORY produces Drives, corporate SOLD_TO End User Company; startDate comes from handoverDate. Exact wire model/formatter/dependency closure is qualified.

Kafka factory config uses StringDeserializer, bootstrap/security settings, poll/backoff declarations. Error handler has shared recoverer and FixedBackOff; CdbDataRejected is explicitly not retryable. Recoverer walks cause chain and logs rejected-data warning or exhausted error; it never publishes to DLQ. Null log key gets UUID only for logging, not broker key mutation. No imported offset/ack guarantee inferred. Gauge callback calls health() when sampled, not at registration. Admin destination is broker cluster, not arbitrary topic payload.

Config default/source declarations are not deployed values. No source build, test, fetch, live endpoint or broker call executed by this review; all files read offline at pinned commit.
