## Q17: event selection, payloads and publication attempts

`messaging/CustomerEventService.java:96–104` returns CUSTOMER_CREATED when previous is null, CUSTOMER_ARCHIVED when updated.archivalData is non-null, CUSTOMER_UPDATED otherwise, in that precedence. `analytics/AnalyticsEventService.java:81–89` uses the same branches with CREATED, DELETED and UPDATED. These values must belong to the correct enum declarations: shared `messaging/CustomerEventType.java:3–7`, and `analytics/model/AnalyticsEvent.java:20–27`; the latter declares JSON values created, updated and deleted. Archived analytics customers therefore use DELETED, without proving physical deletion.

Customer publication lines 38–60 first skip missing Kafka or disabled settings, obtain the branch result from the previous/current inputs, construct CustomerEventPayload from updated.customerId, updated.version and updated.modified, apply metadata/payload to the event and build a message from settings.topicName, updated.customerId, event, VERSION and PRODUCER_ID. Shared `messaging/CustomerEventPayload.java:5` names these positions customerId:String, dataVersion:Integer, timestamp:Instant. Metadata.type is eventType.toString (lines 68–76). sendSafely receives the same Kafka template and message. This is an attempt, with unavailable SDK acknowledgement and codec semantics.

Analytics publication lines 40–68 similarly skips disabled/missing Kafka, derives event type and fleet account from updated, invokes customerMapper.to(updated,fleetAccount), constructs AnalyticsEvent(analyticsCustomer,eventType), and sends the built message to KafkaTemplate.send. thenRun attaches logging; the returned future is ignored by the postprocessor. `analytics/model/AnalyticsEvent.java:8–18` declares event_id:String, event_type:EventType, event_timestamp:Instant, payload:AnalyticsCustomer; its convenience constructor supplies UUID, supplied type, current time and supplied customer in that order.

`analytics/mapper/AnalyticsCustomerMapper.java:21–35` maps customerId, version, created, modified, mapped customerType, market, mapped individuals and mapped corporateEntities in the declared AnalyticsCustomer constructor order (`analytics/model/AnalyticsCustomer.java:7–15`). Inputs to all three mapper calls must refer to the actual customer/fleet formals. `AnalyticsIndividualMapper.java:15–48` and `AnalyticsCorporateEntityMapper.java:15–47` map each source member, return empty lists for null lists and flatten email/phone/address roles to sets (empty sets for null collections). The nested schema types must be AnalyticsIndividual/AnalyticsCorporateEntity, not a copied shape under another type. `AnalyticsCustomerTypeMapper.java:29–57` selects B2C/B2B without fleet, then MOTABILITY, LEASECO, FLEET; this is source mapping, with external Fleet service/generated accessor implementations unobserved.

`config/event/CustomerEventSettings.java:5–6` and `AnalyticsEventSettings.java:5–6` bind prefixes kafka.customer-event and kafka.customer-analytics-event. API `src/main/resources/application.yml` declares enabled true and topic-name app5541-customer-events / app5541-customer-analytics; `application-local.yml` disables both and Kafka generally. Producer config declarations condition each producer on the corresponding enabled property, construct typed KafkaTemplates and declare JacksonJsonSerializer. Imported SDK base configuration and Spring property precedence in a deployed environment remain unobserved. Topic defaults are source declarations, not proof of an effective environment or delivery.

Required clauses: complete ordered branches with typed enum/wire values; previous/current lexical and helper argument lineage; declared payload shapes including nested types and constructor/mapper lineage; payload/event/message/send propagation with exact topic selectors; settings/configuration/resource joins; explicit source limits for runtime configuration, codec and delivery. Display spelling or presence of a same-named call cannot substitute for these relations.

## Q18: deletion subscription, payload and effects

`messaging/consumer/DeleteCustomerEventConsumer.java:17–32` is conditional on DeleteCustomerEventConfig. Its KafkaListener declares topic `${kafka.delete-customer-event.topic-name}`, group `${kafka.delete-customer-event.group-id}` and factory deleteCustomerConsumerFactory. The payload formal is String eventJson. deserialize(eventJson) returns the local event; metadata correlation is passed to LogUtils, then event.getPayload().customerId is passed to customerService.deleteCustomer. There is no local event-type discriminator or catch. Successful-looking logs do not establish deletion or acknowledgement.

`DeleteCustomerEventDeserializer.java:15–28` declares TypeReference<Event<DeleteCustomerEventPayload>>, passes the incoming json formal and that reference to JsonMapper.readValue, and returns its result. JacksonException is caught, logged and wrapped in CustomerServiceException with the original cause. The diagnostic message misleadingly says PaymentEventPayload; the typed target remains DeleteCustomerEventPayload. `DeleteCustomerEventPayload.java:3` declares its sole field customerId:String. External Jackson configuration, malformed/missing/null payload handling beyond this source catch and broker redelivery are unknown.

`config/event/DeleteCustomerEventConfig.java:14–28` is conditional on kafka.delete-customer-event.enabled=true. Its bean deleteCustomerConsumerFactory returns ConcurrentKafkaListenerContainerFactory<String,String>, builds KafkaConsumerEventSettings with reconnectBackoff and reconnectBackoffMax, then calls inherited buildListenerContainerFactory(kafkaSettings,consumerEventSettings,null). The dependency implementation, error handler, ack mode, dead-letter and retry/redelivery policy are unavailable. Reconnect backoff is not a source retry guarantee for failed business handling.

`DeleteCustomerEventSettings.java:5–12` declares the property prefix and enabled/topic/group/reconnect fields. API application.yml declares enabled true, topic app5541-delete-customer-events, group app5541-customer-integration-api, reconnect 1000 and maximum 30000; application-local.yml disables the consumer and overrides group with app5541-customer-integration-api-local. These are configured source defaults and overrides, not observed runtime state.

`customer/CustomerService.java:246–249` passes its customerId formal directly to customerRepository.deleteByCustomerId. The concrete repository declares the derived Mongo delete operation. This path attempts deletion of the active customer; it does not call archive deletion, audit writing or postprocessing/publication. There is no local catch, transaction or compensation on the two source methods. A synchronous deserialisation failure prevents subsequent statements; a synchronous delete failure escapes the consumer. Broker handling and durable Mongo completion remain unobserved.

Required clauses: listener and activation declarations joined through exact container bean/configuration/settings/resource sources; String input through the exact deserialiser target TypeReference and payload schema; returned-event and customerId propagation across exact call/argument/formal/reference links; resulting repository delete attempt and local failure handling, with unavailable container/dependency policy explicitly unknown. Unknown runtime guarantees are a valid source boundary, not a permanently false clause or an invented guarantee.
