## Q19

`OrderUpdateEventConsumer.java:41–69` deserialises before either branch. CustomerUpdate takes precedence and returns after unarchive handling. Its predicate (`72–76`) requires non-null payload, category `CustomerUpdate` and nonblank customer ID; it does not require BASIC, ORDERCHANGEEVENT or a terminal order status. Ordinary admission (`127–133`) requires non-null payload, status in COMPLETED/CANCELLED/ABANDONED, event type ORDERCHANGEEVENT, order type BASIC and nonblank customer ID. Other categories are not excluded from this ordinary predicate. The mapping (`117–125`) is ORDER_COMPLETED, ORDER_CANCELLED and ABANDONED respectively; default throws IllegalArgumentException. The admitted ordinary branch passes event.customerId and the mapped reason to markForArchival, catching CustomerServiceException.

Unarchive (`78–99`) reads the active customer and returns if archivalData is null; otherwise it clears archivalData and saves the updated customer. CustomerNotFoundException alone selects restore; a sibling CustomerServiceException catch logs. Restore (`101–115`) passes event.customerId and false to CustomerArchiveService.restoreCustomerFromArchive and catches CustomerServiceException. Runtime Kafka acknowledgement and redelivery are not established by these local catches.

Adversarial requirements: preserve typed constant references (not only their spelling), priority/return, every AND conjunct, switch selector and arms, actual/formal applications, updated builder value reaching save, exact false restore argument, and distinct catch targets. A global catch inventory is insufficient.

`CustomerArchiveJob.java:9–35` declares ConditionalOnBean(CustomerArchiveScheduler.class) and Async(customerArchiveJobTaskExecutor). Async activation is declared in AsyncConfiguration. External receiver interception, effective executor selection and scheduling remain unverified. The scheduled invocation's lock does not establish locking throughout asynchronous work: dispatch can return before job completion. Neither max pool 1 nor the annotated lock proves global full-job mutual exclusion.

Job start creates statistics within a try, passes it to findAndArchiveCustomers, and logs counters/duration. Its catch(Exception) logs an outer job failure. `CustomerArchiveService.java:31–48` obtains ready customers and forEach invokes the helper with customer and shared statistics. Each helper attempt tries upsertCustomerArchive(customer), deleteCustomer(customer.customerId()), addExpired and success log, in that order; catch(Exception) calls addFailed then warns. A caught per-customer exception normally allows iteration to continue. Upsert-before-delete creates a possible dual-record window; delete failure leaves the archive attempt in place. No atomic transaction/rollback is declared here. Failures obtaining/iterating the candidates, or failures from catch/statistics/logging, need not continue; they can reach the outer job catch. An exception after addExpired (for example from the success log) can also reach addFailed, so the counters need not be mutually exclusive. Counters describe local attempts, not durable success.

Adversarial requirements: exact annotation ownership/imports and resource joins, activation and provider evidence, named async executor and ignored dispatch, typed pool literals, full loop callback/customer/statistics actual-formal lineage, catch scope/type and ordered success/failure counters. Mutation rejection counts only applied changes to a complete passing whole-question baseline. Page ordering must not select a different overload.
