# Scan readiness source review

A readiness verdict concerns a bounded repository source pass. The wider scan queue remains stopped.

This independent contract was fixed from the implemented pipeline before evaluating the new readiness driver. The source audit reads Groundwork code, retained fixed benchmark artefacts, and only the previously authorised customer-service revision `09623ab3a1f39845d8fc02abc3d591b53a3b5fea`. It does not authorise another repository, a broader scan, a fetch, Maven, an application build or application execution.

## What readiness means

`READY_FOR_BOUNDED_REPOSITORY_PASS` requires the mechanical and evidence gates below. It means the implementation can attempt an explicitly authorised, pinned repository within declared bounds and report incomplete knowledge honestly. It does not mean every endpoint, source question, runtime behaviour or actor journey is known.

`READY_TO_WIDER_SCAN` additionally requires explicit user authorisation for the named wider scope. It is false here. A passing benchmark, a readiness receipt, an available model quota or a successful bounded capture cannot resume the stopped queue.

The frozen reference remains three scopes, twenty-seven files, nine questions and nineteen semantic checks. Every check must have its passing baseline and an applied destructive mutation that fails or becomes unresolved. The customer-service review remains twenty-two questions: thirteen supported, eight partial and one unsupported. All original questions and required evidence clauses stay unchanged. The earlier 182 mutations and the Q19/Q20 additions are separate from the nineteen depth checks; one denominator cannot replace another.

## Required gates

1. **Evidence and claims.** Verify complete bounded pages, source pins, current analysis fingerprints, the exact fixed benchmark roster and all required baseline/mutation results. Schema validity, retained source bytes, inventory coverage and a zero exit code do not establish semantic acceptance. Parser diagnostics quarantine semantics; unsupported resources and oversized records remain explicit. Supported source answers retain external/runtime gaps. Partial, unknown, not examined and unsupported states cannot be counted as green answers. Q21 remains unsupported in the source-proof tally when its source obligations are unclosed. The interpretation phase must nevertheless make a best-effort, grounded INFERRED actor/journey proposal from the surrounding system context, with confidence, rationale, alternatives and dependencies. Inference is useful knowledge and must be labelled separately from observed source facts or runtime guarantees.
2. **Automatic bounded inspection.** Discover supported source entry declarations deterministically and expose their native evidence on demand. Record the discovery denominator, exclusions, ownership, pagination and limits. The hand-maintained 151-selector customer-service roster is a regression oracle, not the generic repository selection strategy. A discovered entry is a declaration, not an accepted endpoint or complete execution closure. Hitting a selection/page/byte bound must produce an explicit incomplete result, never silently omit entries.
3. **Resource and quota policy.** Precheck every selected source's pinned byte size before reading any selected blob, retained source/index cache, parser or fingerprint. Default selected-source limit is 1 MiB; an explicit override is bounded by the existing 32 MiB Git output limit and participates in configuration provenance. Oversize failure carries the path, blob, actual bytes and limit. Ancillary/GraphQL resources keep their separate bounds. Native parser timeout/output caps, unsupported parser diagnostics and oversized query records cannot be hidden by a green aggregate. Deterministic extraction currently makes zero runtime model calls/tokens. Required LLM interpretation is a separate phase with its own measured usage, or explicitly unknown usage; it cannot inherit the extractor's zero. Dispatch/context budgets, unavailable-model state and stop/resume state remain explicit. Unknown token usage is allowed and reported as unmetered; it must not be described as verified token-cost budget compliance or copied to zero. Enforced source/query/materialisation bounds are checked separately. Source-byte limits do not establish an aggregate heap or cached-index size bound.
4. **Checkpoint and stop integrity.** A checkpoint fixes repository, commit/tree, source inventory/selection, analysis configuration and toolchain/rule fingerprints. Completed shards remain immutable. Interruption, budget failure and parser/resource failures cannot select a complete aggregate. Resume verifies prior artefacts and all identities before reusing completed work; a mismatch fails rather than replacing the checkpoint's pin. A stop is recorded and does not automatically resume. The wider queue's stopped state is independent of a repository checkpoint.
5. **Incremental behaviour.** Exercise changed, added, same-blob renamed and deleted files in an isolated synthetic repository. Preserve unchanged bytes/indexes where declared, refresh renamed anchors, retire deleted facts/scopes and invalidate added-file negative searches and affected dependency closures. Rule/configuration/schema changes must regenerate affected analysis without unnecessary parsing; parser/runtime changes must reparse retained source without unnecessary Git blob reads. Missing closure widens analysis conservatively. Repository inventory changes are distinct from a fixed selected-scope refresh, whose current explicit rename/delete stop and added-file non-expansion are valid limits rather than repository-wide discovery.

## Audited starting gaps

Before the readiness work, `tools/scan-repository.ts` used a new output directory and published its aggregate only after every cold/first and warm shard. Immutable per-shard selections survived interruption, but there was no repository checkpoint/resume/stop contract. `tools/scan-refresh.ts` refreshed only its explicit scope, rejected selected rename/deletion and did not add newly discovered files. `src/domain/scan/freshness-plan.ts` already provided conservative dependency/negative-search invalidation, but that planner was not a repository refresh orchestrator.

`src/infrastructure/scan/scoped-source-git.ts` read selected blobs without a metadata size precheck. The ancillary reader already checked a 1 MiB bound before reading bytes. `src/infrastructure/scan/source-index.ts` already capped native parser execution at sixty seconds and output at 32 MiB; Go parsing disables proxy downloads and module/workspace resolution. Git readers disable lazy fetching, prompts and optional locks. TypeScript parsing and cached JSON did not have corresponding time/aggregate memory bounds. These distinctions must remain visible after adding the selected-source budget.

Spring bindings already retain typed routes, schemas, security declarations, calls/values, stores, outbound requests, configuration, async and schedules. Their native execution evidence depended on explicit method/field selectors. The successful customer-service review therefore did not itself establish automatic repository entry discovery or arbitrary whole-program closure.

## Remaining customer-service source questions

Q04 is partly an inspection/lineage gap. Pinned `common/EntityFactory.java:36–69` distinguishes update(null updates), which returns null, from patch(null updates), which returns the current value. `customer/CustomerFactory.java:67–129` uses direct request fields/default false for update and request/current fallbacks for patch. Complete list, individual and corporate policies need their own bounded cross-call proof. Generated accessors and effective omitted-versus-null wire binding remain explicit boundaries; source inspection cannot fabricate them.

Q06 is likewise source-inspectable: `EntityFactory.java:21–26` dispatches duplication; `CustomerFactory.java:48–64` constructs the customer with a generated ID and delegates nested duplication. `individual/IndividualFactory.java:108–133` and `company/CorporateEntityFactory.java:62–81` expose changed identifiers and preserved constructor fields. Nested external-user-ID duplication, inherited dispatch, constructor fields and the service result require actual/formal and value lineage. An ID-generation call does not prove runtime uniqueness.

Q10 has an adapter gap beyond missing native slices. `auditlog/AuditLogService.java:21–35` constructs PageRequest.of(page, limit), invokes findAllByCustomerIdOrderByVersionDesc and constructs pagination/results. `AuditLogRepository.java:12–15` declares the two derived queries. The current Mongo adapter classifies operation names and explicit Criteria/Update expressions; it does not retain a typed derived-query customer/version predicate and descending-version sort contract. A method name alone cannot become an effective Mongo sort guarantee.

Q11 can expose more local source behaviour, but cannot establish complete security acceptance from these declarations. `api/security/TrustedIssuerHandlerInterceptor.java:27–33` reads the named header and invokes validation only when hasText. `security/TrustedIssuerValidator.java:25–40,105–112` parses and checks the issuer; the selected body contains no signature-verification invocation. `security/UserIdentityResolver.java:32–55` wraps the Volvo token and dispatches Connect/Entra decoding, rethrowing expired-token failures and logging other runtime decoder failures. Effective HTTP security, external decoder implementation, generated configuration and runtime activation remain unclosed. Do not turn an issuer allow-list into a verified authentication claim.

## Adversarial acceptance cases

Reject a readiness receipt that omits or duplicates a frozen check, uses an unapplied mutation, changes a question's required evidence, calls thirteen supported questions “complete”, labels inferred Q21 actors/journeys as observed or proven from role strings alone, equates local freshness with remote/deployed currency, or sets wider restart true without explicit authorisation.

Reject a source pass that reads a small first file before discovering an oversized later file; bypasses a smaller policy through a retained index; treats character count as UTF-8 byte size; silently drops an oversized entry/page; interprets parser recovery as semantic evidence; resumes a moved pin, altered manifest or corrupted completed shard; loses an added/deleted file; retains old rename anchors; or treats a rule change as unchanged analysis.

The selected-source budget's focused tests exercise exact bounds, invalid metadata/policies, typed failure fields, all-file preflight before cache/blob access, reduced-budget cache bypass, multibyte bytes/unusual Git paths and provenance invalidation. Readiness-driver tests must exercise its actual implemented API before any ready verdict is accepted.

## Interpretation boundary

The user's steering requires best-effort interpretation of purpose, actors and journeys, using the source and surrounding system context. Do not refuse useful interpretation merely because intent is not explicitly declared. An interpretation sidecar must retain its evidence anchors, contextual assumptions, confidence, rationale, plausible alternatives and dependencies. It may support a useful informed answer to Q21 while Q21's stricter source-proof receipt remains unsupported. The sidecar must not rewrite an unclosed source obligation as a verified fact, impersonate runtime observation, silently select a deployment or invent a success guarantee. Missing or contradictory evidence lowers confidence or records alternatives; it does not justify unlabelled certainty.

Model usage for interpretation is measured where available and explicitly unknown otherwise. An unavailable model or exhausted budget produces an incomplete/stopped interpretation phase, not a fabricated empty sidecar or a false zero-use success. A deterministic extraction receipt's zero model count says nothing about the agent effort used to interpret the system.

## Focused audit result

The implementation passes forty-two focused tests across selected-source budgets (six), whole-repository delta planning (seven), repository checkpoint/resume orchestration (eight), the inference boundary (four), the pure readiness assessor (nine) and verified ancillary caching (eight). The delta tests include real synthetic Git changes and observed cache reuse. The checkpoint tests preserve all six committed artefact hashes and modification times, ignore abandoned attempt directories, stop before selecting an aggregate, and reject corrupt scope/publication/terminal-task data before new source work. The predecessor pass retains old shard membership and appends new files rather than rechunking unchanged source.

Two checkpoint defects were found and repaired during this audit: prepared scope files were initially ignored during resume, and a corrupt terminal checkpoint could re-execute missing tasks before rejecting its aggregate. The independent tests now reject both before extraction. Two inference provenance defects were likewise repaired: scan context pins must agree with actual snapshot sources, and purpose/relationship entity contexts must have been supplied to their run. Grounded inferred claims remain valid; observed-label promotion, copied zero model usage, missing interpretation areas, dependency cycles and pending-with-completed-work are rejected.

These tests establish the stated bounded mechanisms, not a wider restart or complete system knowledge. A final readiness receipt must still name current benchmark/regression evidence and analysis fingerprints. Historical accepted captures retain their original provenance; unchanged source revision alone cannot make them current after parser/rule changes. The wider queue remains stopped until the user explicitly authorises a named scope.

The pure assessor checks the exact three-scope/nineteen-check/twenty-two-question denominator shapes and uniqueness; the I/O caller must additionally verify the frozen manifest and question/evidence hashes. It requires positive workflow evidence, at least two distinct verified bounded entry queries, complete returned evidence within the fixed four-record/64 KiB/thirty-two-ID page caps, and known enforced source/query/materialisation bounds. Runtime frontiers can remain partial. Every interpretation attempt must have received a verified target scan context for the assessed repository and commit. Unknown interpretation token usage remains accepted as explicitly unmetered; the assessor does not claim token-cost budget compliance. Its result always leaves wider scans stopped and unauthorised.

The optional ancillary cache stores raw bytes only, including bytes classified as binary exclusions. Every file still receives a fresh pinned metadata size check before any cache read. Cache envelopes are bounded regular files; a hit requires exact expected size, canonical base64 and the complete Git blob hash. Symlinks, oversized entries, corrupt metadata or mismatched content cannot establish a hit. Invalid entries fall back to pinned Git bytes. Per-file `git`/`cache`/`none` origins and aggregate read/hit counts distinguish actual work. Tests prove zero warm Git blob reads for unchanged text, binary exclusions and same-blob renames, a single read for a changed blob, corrupt-cache rebuilding and unchanged no-cache behaviour. This cache does not interpret retained YAML/XML or convert binary/text retention into semantic source claims.
