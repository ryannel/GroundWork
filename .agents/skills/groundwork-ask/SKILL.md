# Ask the map

Groundwork's system model is a map of what runs, with every extracted fact pinned to a file, lines and commit.
Answer from the map first, then check the cited code, and say how fresh the answer is. Reading the map is fast and
cheap; searching a dozen repos is not.

## 1. Find it in the map

Start with the workspace's `MAP.md` (`workspaces/<ws>/MAP.md`, generated by `npm run map -- md`): the repos
and the commit each was read at, then domains › systems › components, one line each. Then ask the map; every
command prints JSON:

```bash
npm run map -- <command> --workspace <ws> [--checkouts ~/.cache/groundwork/clones/<org>]
```

| Question                                       | Command                                                                                         |
| ---------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| where is X, what is it called                  | `find <words>`: facts whose id, name or summary hold the words                                  |
| what is this, what does it touch               | `show <id>`: the fact, its sources as permalinks, what it calls and what calls it, and when     |
| who depends on this endpoint, message or store | `callers <id>`: who reaches it, up to `--depth` hops (3)                                        |
| what happens when it is called                 | `calls <id>`: the call tree under an endpoint, message or handler, through each handler's steps |
| what does this file hold                       | `owns <path>` (`--repo org/name` to narrow): the facts read from it                             |
| how fresh is the map                           | `repos`: the commit each repo was last read at; never-scanned repos say so                      |

`--checkouts <dir>` adds a local path to every source whose repo is checked out as `<dir>/<name>`, so you can
open it straight away. For "how does A reach B", run `calls` on A's entrypoints and look for B, or `callers` on B.

If the map cannot answer, read the YAML directly:

- `workspaces/<ws>/domains/<d>/systems/<s>/system.yaml`: the system, its team, repos and components;
- `contracts.yaml` next to it: stores, interfaces and endpoints, schemas, messages, each with `sources`;
- `handlers.yaml` next to it: what runs on each endpoint, message, job and UI action, as a step tree;
- `workspaces/<ws>/flows/` and `journeys/`: curated walks across components;
- `node tools/sources.ts workspaces/<ws> --index [--repo org/name]`: every fact with its sources, as JSON;
- `grep -rn "<id>" workspaces/<ws>`: who mentions an id.

Ids have a prefix by kind: `svc:` component, `st:` store, `if:` interface, `api:` endpoint, `sch:` schema,
`msg:` message, `h:` handler, `flow:`, `team:`. `[[id]]` in prose is a reference.

## 2. Check it in the code

For anything the answer depends on, open the cited file at the cited lines. A source is
`{ repo, path, lines, commit, symbol? }`:

- locally: the clone is at `${GROUNDWORK_CACHE:-$HOME/.cache/groundwork}/clones/<org>/<name>` (or wherever
  `MAP.md` says); read `git -C <clone> show <commit>:<path>` around the lines, and compare with HEAD if it
  matters;
- remotely: `https://github.com/<org>/<name>/blob/<commit>/<path>#L<from>-L<to>`, or
  `gh api repos/<org>/<name>/contents/<path>?ref=<commit>`.

If the code says something different from the map, trust the code, say so, and suggest a re-scan of that repo
(`/groundwork-scan <ws> --since`). Facts with `origin: seeded` have no code behind them yet: say the answer is
from the demo or seed data.

## 3. Say how fresh it is

Each repo's scan file, `workspaces/<ws>/scans/<org>/<name>.yaml`, holds the `head` the map reflects. Compare it
with the branch tip: `npm run map -- repos` gives the head, `git ls-remote https://github.com/<org>/<name>.git
refs/heads/<branch>` the tip, and `git -C <clone> rev-list --count <head>..origin/<branch>` the distance. When the repo is
behind, say so with the answer: "as of 3f9c2e1, 37 commits behind". When there is no scan file, the facts for
that repo were not scanned.

## Answer

Lead with the answer in plain words. Then the evidence: the ids, and a permalink for each claim that matters.
Then freshness, and anything the map does not know (a question to the owning team from `system.yaml`'s `team`).
Keep it short: a newcomer should be able to act on it.
